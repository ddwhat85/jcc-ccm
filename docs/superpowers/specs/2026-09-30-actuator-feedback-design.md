# 출력 작동 확인(피드백) — 벤트가 정말 열렸는가

작성 2026-09-30 · 대상 JCC-CCM · 선행: 엣지 예지(벤트·히터·팬 구동), 튜닝 콘솔

## 1. 목표

지금 CCM은 릴레이 코일에 "열어라"를 **쓰기만** 한다. 릴레이 고착·배선 탈락·모듈 재부팅·댐퍼 걸림이
있어도 화면은 "벤트 개방"이라고 말한다 — 화재 예지 제품에서 가장 위험한 거짓말이다.
명령 뒤 실제 상태를 확인하고, 다르면 스스로 다시 시도하고, 끝내 안 되면 **작동 실패 경보**를 낸다.

## 2. 성공 기준

- 명령한 상태와 실제 상태가 작동 시간(기본 벤트 30초) 뒤에도 다르면, 재시도 2회 후 '작동 실패'가
  서버 위험 경보·알림으로 올라간다. 인터넷이 끊겨 있어도 CCM은 확인·재시도를 계속한다.
- 릴레이 모듈이 재부팅돼 코일이 풀려도 30초 안에 알아채고 다시 쓴다(이벤트 '릴레이 상태 복구').
- 명령 없이 위치가 바뀌면(사람이 손으로 닫음 등) 주의 이벤트.
- 대시보드 예지 카드에 출력별 '확인됨 / 작동 중 / 작동 실패 / 확인 안 함'.
- 실제와 명령이 다시 맞으면 경보가 자동 해소된다.

## 3. 확인 방식 (출력별 설정)

| feedback | 읽는 것 | 확인 범위 |
|---|---|---|
| `none` | 없음 | 확인 안 함(화면에 '확인 안 함') — log 드라이버·시운전 |
| `coil` (modbus_coil 기본) | 같은 코일 되읽기(Modbus FC01) | 릴레이가 명령대로 붙었나 + 모듈 재부팅 풀림 |
| `switch` | 위치 스위치(보조접점) → 릴레이 모듈 입력(FC02 discrete input) | **실제로 열렸나/닫혔나** |

권장 구성(견적·설치 가이드): 보조접점 달린 댐퍼 구동기 + 입력 단자 있는 Modbus 릴레이 모듈 → `switch`.
설정: `feedback`, `feedback_slave`(기본 = 릴레이와 같은 슬레이브), `feedback_input`, `feedback_invert`,
`travel_seconds`(벤트 30, 히터·팬 3), `retries`(2), `check_every`(30초).

## 4. 동작 (CCM `ActuatorGuard`, 출력마다 하나)

상태: `ok`(확인됨) · `moving`(작동 중) · `fault`(작동 실패) · `unknown`(확인 안 함/읽기 실패).

1. **명령 시**: 쓰기 성공 → `moving`, 기한 = now + travel_seconds.
2. **매 주기**: 기한 전 `moving`이면 대기(스위치는 기한 전에 맞으면 바로 `ok`). 기한이 지나면 읽기:
   - 맞음 → `ok`(이전이 `fault`였으면 '복구' 이벤트)
   - 다름 → 재시도 남았으면 다시 쓰고 `moving`(재시도 −1), 없으면 `fault` 확정(사유: "명령 개방·실제 닫힘" 등)
   - 읽기 실패(통신) → `unknown`(이번 주기는 판단 보류, 다음 주기 재시도 — 통신 문제를 고장으로 단정하지 않음)
3. **평소 감시**: `ok` 상태에서 check_every마다 읽기. 코일이 명령과 다르면(모듈 재부팅) 다시 쓰고
   '릴레이 상태 복구' 이벤트. 스위치 위치가 명령 없이 바뀌면 '명령 없이 위치 바뀜' 주의 이벤트 후 명령대로 재구동.
4. **`fault` 중**: check_every마다 한 번 다시 써 본다(현장에서 고쳤으면 스스로 풀림). 연속 쓰기로 구동기를
   혹사하지 않게 주기 제한.
5. 버스는 센서와 같은 RS485·락(shared_bus) — 읽기 추가는 출력당 check_every에 1회.

## 5. 보고·서버

- 엣지 보고 `actuators[kind]`에 `confirm`, `position`(스위치일 때 "open"/"closed"), `fault`(사유) 추가.
- 서버 `ingest_edge`: confirm이 `fault`로 바뀌면 `raise_alarm(dev, kind, "actuator_fault", "벤트 작동 실패 — 사유")`
  (위험 → 기존 상향·카카오/SMS 경로), `ok`로 돌아오면 해소. 이벤트 `actuator_fault`/`actuator_fault_clear`,
  CCM의 복구·위치 변화 이벤트는 기존 `edge_actuate` 행에 실어 `edge_actuate`로 기록.
- 경보 원인 묶기: 같은 판넬에 화재 사건이 열려 있으면 벤트 작동 실패는 그 화재 사건에 묶인다(원인은 화재, 문제는 벤트).
- 대시보드 예지 카드: 출력 버튼 아래 작은 표시 '확인됨 / 작동 중 / 작동 실패'(작동 실패는 빨강 + 사유 툴팁).
- 데모: `JCC_DEMO.episode("vent_stuck")` — 벤트를 걸리게 해 화면에서 작동 실패 경보를 볼 수 있게.

## 6. 범위 밖

- 모터 전류로 걸림 감지(전류 센서 필요) · 대체 조치(차단기 트립 등) · 튜닝 시나리오화(기준값 문제가 아님).

## 7. 테스트

- 펌웨어 단위(가상 릴레이에 고장 주입 — 걸림·코일 풀림·느린 구동·읽기 실패): 정상 확인, 느린 구동은
  기한 안이면 ok, 걸림 → 재시도 2회 후 fault, fault 중 수리 → 자동 복구, 모듈 재부팅 풀림 → 재기록·이벤트,
  수동 위치 변화 → 이벤트·재구동, 통신 실패는 unknown(고장 아님), feedback none은 확인 안 함.
- 설정 검증: switch인데 입력 번호 없음 → 오류, travel_seconds 범위.
- 종단(실제 HTTP): CCM 벤트 걸림 → 서버 위험 경보 → 수리 → 해소.
- 서버: 화재 사건과 묶임(incidents), 이벤트 라벨.
