# 예지 튜닝 콘솔 + 원격 설정 적용 설계

작성 2026-09-29 · 대상 JCC-CCM (스마트 판넬 모니터링) · 선행: 2026-09-23 화재 징조 예지 설계

## 1. 목표

음악 프로그램의 믹서처럼, 예지 알고리즘(화재·접점발열·결로)의 **기준값 손잡이를 돌리면 판정이
어떻게 바뀌는지 즉시 보여주고**, 마음에 드는 값을 **버튼 하나로 서버와 모든 CCM에 적용**한다.

지금 기준값은 문헌값·가정이다. 이 콘솔은 (1) 오경보를 줄이면서 사고는 놓치지 않는 값을 찾는
도구이고, (2) 실센서 기록이 들어오면 그대로 교정 도구가 된다.

## 2. 성공 기준

- 손잡이를 놓은 뒤 0.3초 안에 모든 시나리오 결과(타임라인·성적표)가 다시 그려진다.
- 미리보기(브라우저 JS)와 서버 재검증(파이썬 정본)의 성적표가 같다(테스트로 보장).
- **사고 시나리오를 하나라도 놓치는 값은 적용되지 않는다.** 관문은 서버가 판정한다 —
  화면을 조작해도 뚫리지 않는다.
- CCM은 펌웨어에 박힌 **절대 한계** 밖의 값은 거부한다. 서버가 뚫려도 감지를 끌 수 없다.
- 적용·거부·되돌리기가 모두 기록되고, 어느 CCM이 어느 설정 버전인지 대시보드에서 보인다.
- 한 번에 이전 버전(또는 기본값)으로 되돌릴 수 있다.

## 3. 사용 흐름

1. 대시보드 **튜닝** 화면을 연다. A = 지금 적용된 설정 버전, B = 편집 중인 초안(처음엔 A와 같음).
2. 손잡이를 돌린다 → 브라우저가 11개 시나리오를 B로 다시 돌려 타임라인 A/B 겹침과 성적표를 갱신.
3. 시나리오 칩(통과=평상, 놓침·오경보=빨강)을 눌러 해당 타임라인을 본다.
4. **적용** → 서버가 범위·한계·관계 검사 → 파이썬 정본으로 전 시나리오 재검증 → 통과 시 새 버전
   저장·활성화, 서버 예지 엔진에 즉시 반영 → 다음 텔레메트리 응답으로 각 CCM에 전달.
5. CCM이 검증 후 적용하고 "설정 v7 적용됨"(또는 거부 사유)을 보고 → 화면에 CCM별 상태 표시.
6. 문제가 있으면 버전 목록에서 **되돌리기**(같은 관문을 거친다).

## 4. 구조

```
[튜닝 화면] 손잡이 ─▶ JS 코어(기준값 주입) ─▶ 시나리오 재생 ─▶ 타임라인 A/B + 성적표
     │ 적용(초안, 기준 버전)
     ▼
[서버] 레지스트리 검사(범위·절대 한계·관계) ─▶ tuning_eval(파이썬 정본) 전 시나리오
       ─▶ 놓친 사고 0? ─ 아니오 ─▶ 409 + 성적표
                        └ 예 ─▶ tuning_config v(n+1) 저장·활성 ─▶ Predictor.reconfigure
     │ 텔레메트리 응답 {tuning:{version, params}} (CCM 보고 버전 ≠ 활성 버전일 때만)
     ▼
[CCM] 레지스트리 절대 한계 검사 ─▶ EdgePredictor.reconfigure ─▶ 상태파일 저장
       ─▶ 다음 페이로드 {tuning:{version, status:"ok"|"rejected", error}}
```

단위(각각 한 가지 일만 한다):

| 단위 | 위치 | 하는 일 |
|---|---|---|
| `params.py` 파라미터 레지스트리 | 서버 코어 → 펌웨어 바이트 동일 사본(sync_edge_core) | 손잡이 목록·기본값·화면 범위·절대 한계·관계 규칙, `validate(params)`, `apply_to(cfgs, params)` |
| `scenarios.py` 시나리오 라이브러리 | 서버 | 결정적(시드 고정) 시계열 생성 + 시나리오별 기대(잡아야 할 것/내면 안 되는 것) |
| `tuning_eval.py` 평가기 | 서버 | 시나리오를 `build_panel_inputs`→`Predictor`로 한 틱씩 재생 → 사건 목록 → 성적표 |
| 설정 버전 저장 | `storage.py` `tuning_config` 테이블 | 버전·값·작성자·메모·성적표·시각, 활성 버전 |
| API | `app.py` | 아래 6절 |
| JS 미러 | `web/demo-api.js` + `server/static/index.html` | 코어에 cfg 주입, 재생·성적표(미리보기), 데모 모드용 `/api/tuning/*` |
| CCM 수신 | `firmware/jcc_ccm/edge.py`, `http_transport.py`, `agent.py` | 수신·검증·적용·저장·보고 |

**시나리오 시계열은 서버가 JSON으로 내려준다**(`/api/tuning/scenarios`, 정적 데모는 빌드 때 삽입).
브라우저는 판정만 돌린다 → 생성기를 JS로 또 만들 필요가 없고, 시험지가 한 벌뿐이다.

**절대 한계는 `params.py`에 있고 펌웨어에는 바이트 동일 사본으로 들어간다.** 펌웨어 코드는 서명된
OTA로만 바뀌므로, 한계를 바꾸려면 JCC 오프라인 키 서명이 필요하다. 서버가 보내는 설정은 한계
안에서만 움직인다.

## 5. 손잡이 (레지스트리)

튜닝 대상은 판정 기준만이다. 입력 보호(워밍업·끊김 판정)와 접점 학습 파라미터는 손잡이에서
뺀다(학습 중 바꾸면 기준이 오염된다 — 필요하면 코드 변경으로).

| 그룹 | 손잡이 | 기본 | 절대 한계(제안) |
|---|---|---|---|
| 화재·가스 | H2 warn/alarm/rise_warn/rise_alarm (%LEL) | 10/25/3/10 | alarm ≤ 50 |
| | VOC warn/alarm/rise_warn/rise_alarm (ppm) | 200/1000/100/400 | alarm ≤ 2000 |
| | CO warn/alarm/rise_warn/rise_alarm (ppm) | 50/200/20/80 | alarm ≤ 400 |
| 화재·융합 | w_h2 / w_voc / w_co / w_temp | 0.38/0.38/0.32/0.10 | w_h2·w_voc·w_co ≥ 0.2 |
| | pair_boost / conf_boost | 0.20/0.15 | 0~0.5 |
| | temp_rise_warn/alarm (°C/분) | 1/5 | alarm ≤ 10 |
| | z_lo / z_hi | 3/6 | z_hi ≤ 10 |
| 화재·단계 | watch / open(벤트) / close / crit (FRI) | 30/55/20/80 | open ≤ 70, crit ≤ 90 |
| | over_hold 경보치 초과 지속(초) | 60 | ≤ 120 |
| 접점 | i_min (A) | 2 | ≤ 5 |
| | res_warn / res_alarm (°C) | 5/11 | res_alarm ≤ 20 |
| | t_abs_alarm (°C) | 60 | ≤ 80 |
| | rise_warn (°C/분) | 0.3 | ≤ 1 |
| 결로 | margin_warn / margin_alarm (°C) | 3/1 | margin_alarm ≥ 0.5 |
| | rh_high (%) | 80 | ≤ 90 |
| | fall_warn / horizon_min / trend_cap | 0.4/10/6 | horizon ≥ 5 |

관계 규칙(위반 시 거부): 각 가스 warn < alarm, rise_warn < rise_alarm · close < watch < open < crit ·
res_warn < res_alarm · margin_alarm < margin_warn · z_lo < z_hi.

화면 범위는 절대 한계보다 좁다(손잡이 끝이 곧 한계가 되지 않게). 한계값은 이 문서의 제안이며
구현 전 검토에서 확정한다.

## 6. API

| 메서드 · 경로 | 설명 |
|---|---|
| `GET /api/tuning/params` | 레지스트리(손잡이 목록·기본·화면 범위·한계·단위·설명) |
| `GET /api/tuning/scenarios` | 시나리오 목록 + 시계열 + 기대 |
| `GET /api/tuning/config` | 활성 버전·값 + 버전 이력 + CCM별 적용 상태 |
| `POST /api/tuning/evaluate` | `{params}` → 파이썬 정본 성적표(미리보기 교차확인용, 저장 안 함) |
| `POST /api/tuning/apply` | `{params, base_version, note}` → 200 새 버전 / 400 검사 실패 / 409 관문 실패·버전 충돌 |
| `POST /api/tuning/rollback` | `{version}` 또는 `{version:"default"}` → apply와 같은 관문 |

모두 로그인 필요. `base_version`이 활성 버전과 다르면(누가 먼저 바꿈) 409로 거부하고 새 A를 보여준다.
이벤트: `tuning_apply`, `tuning_reject`, `tuning_rollback`, `tuning_edge`(CCM 적용·거부).

## 7. 시나리오와 성적표

사고(놓치면 적용 불가):

| # | 시나리오 | 잡았다 = |
|---|---|---|
| 1 | 케이블 과열 H2→VOC→온도 | 가스 경보치 도달 시각 전에 벤트 자동 개방 |
| 2 | 절연물 탄화 CO 단독 서서히 | 경보치 도달 전에 화재 '주의' 이상 |
| 3 | 접점 풀림 3주 서서히 | 절대 60°C 도달 전에 접점 '주의' 이상 |
| 4 | 접점 급변(볼트 이완) | 시작 후 10분 안에 접점 '위험' |
| 5 | 장마철 결로 | 여유 0 도달 전에 히터 작동 |
| 6 | 야간 급냉 결로 | 여유 0 도달 전에 팬 또는 히터 작동 |

함정(내면 오경보):

| # | 시나리오 | 오경보 = |
|---|---|---|
| 7 | 청소 스프레이(VOC 30초 튐) | 화재 '위험' 이상 또는 벤트 자동 개방 |
| 8 | 근처 용접(H2·CO 잠깐) | 〃 |
| 9 | 모터 기동(전류 순간 급증) | 접점 '위험' |
| 10 | 여름 한낮(함내온도 서서히) | 화재 '위험' 이상 또는 결로 '위험' |
| 11 | 센서 값 튐·끊김 | 경보 발생(가스 끊김 fail-safe 벤트는 정상 동작으로 인정) |

성적표: 잡은 사고 · 놓친 사고 · 오경보 · 가장 아슬아슬한 선행시간(기준 시각 − 첫 탐지 시각, 분 — 척도가
분~일로 섞여 평균은 쓰지 않는다). 사건 시작 전 탐지는 잡음으로 세지 않는다.
함정에서의 '주의'는 오경보로 세지 않고 참고 숫자로만 보인다.

시나리오는 코드로만 추가·수정한다(대시보드에서 편집 불가 — 시험지를 고쳐 관문을 통과시키는 것을
막는다). 긴 시나리오(3주)는 5분 간격, 짧은 것은 5초 간격으로 표본을 만든다. 실센서 기록은
나중에 같은 형식의 시나리오 파일로 추가한다.

**2026-09-29 첫 재생 결과와 결정**: 기본값이 볼트 이완을 1.8분 늦게 잡고(5/6), 스프레이·용접에서
오경보. → 접점 위험 12→11°C, 경보치 초과 60초 지속 요구(`over_hold`), 용접은 알려진 한계로 기록
(가스만으로 용접 흄과 열폭주 구분 불가 — 현장 용접 중엔 벤트 수동 모드). 같이 발견한 버그: 평소값
6~7개로 z를 계산해 재시작 3분쯤 헛 '주의' → 최소 30개. 기준선 = 사고 6/6 · 오경보는 용접뿐.

**기본값은 CI에서 모든 사고를 잡아야 한다.** 구현 중 기본값이 어떤 시나리오를 놓치면 숨기지 않고
보고한다 — 시나리오를 쉽게 고치는 것이 아니라 근거를 따져 알고리즘·기본값·시나리오 중 무엇이
틀렸는지 판단한다.

## 8. 원격 설정 — 서버와 CCM

- 설정은 레지스트리 전체 값의 스냅숏(부분 변경 없음)이고 정수 버전을 가진다. v0 = 기본값.
- 서버: 활성화 즉시 `Predictor.reconfigure(fire, contact, dew)` — 판넬별 VentController가 들고 있는 cfg 참조까지 교체하되, 판넬 상태(벤트 히스테리시스·
  접점 학습 기준·결로 액추에이터)는 유지하고 기준값만 바꾼다. 활성 버전은 DB에 남아 재시작 후에도 유지.
- 전달: 텔레메트리 요청에 CCM이 `tuning_version`을 싣고, 서버 응답에 다를 때만 `tuning`을 싣는다
  (MQTT는 `jcc/ccm/{id}/cmd`로 같은 내용).
- CCM: `params.validate` 통과해야 적용. 알 수 없는 키·빠진 키·타입 오류·한계 밖·관계 위반 → 통째로
  거부, 이전 설정 유지, 거부 사유 보고. 적용 후 첫 판정에서 예외가 나면 이전 설정으로 되돌리고 보고.
- CCM은 적용한 설정을 `/opt/jcc-ccm/tuning.json`에 원자적으로 저장해 재부팅 후에도 유지한다.
  서버와 끊겨 있어도 마지막 적용 설정으로 계속 판정한다.
- 대시보드: CCM별 "v7 적용됨 / v6 (전달 대기) / 거부: 사유".

## 9. 화면

대시보드에 **튜닝** 화면을 추가한다(기존 알고리즘 내역 화면 옆). 배치는 목업과 같다:

- 위: 시나리오 칩 11개(사고·함정 구분, 결과 색).
- 왼쪽: 그룹별 손잡이. 기본값과 다르면 강조, 두 번 누르면 기본값 복귀, 화면 범위 밖으로 안 움직임.
- 가운데: 선택 시나리오 타임라인 — 알고리즘에 맞는 지표(FRI·접점 잔차·결로 여유), 기준선,
  A(회색)·B(파랑) 겹침, 사건 표시(주의·위험·벤트·히터), 사고 기준 시각 표시.
- 오른쪽: 성적표 A → B, 좋아짐·나빠짐 색.
- 아래: 관문 상태(놓친 사고 수·한계 검사), 메모 입력, **기본값으로 · 되돌리기 · 적용** 버튼,
  버전 이력과 CCM별 적용 상태.
- 디자인 규칙: 기존 대시보드 토큰 사용, side-tab·dark-glow·레이아웃 속성 애니메이션·이모지 아이콘 금지.

## 10. 오류 처리

| 상황 | 동작 |
|---|---|
| 미리보기와 서버 성적표가 다름 | 서버 결과를 따르고 화면에 "미리보기 불일치" 경고 표시(패리티 버그 신호) |
| 관문 실패 | 409 + 놓친 시나리오 목록, 적용 안 함, `tuning_reject` 기록 |
| 동시 편집 충돌 | 409, 화면이 새 A를 불러오고 초안은 유지 |
| CCM 거부 | CCM은 이전 설정 유지, 서버에 사유 기록, 경보 패널에 '설정 거부' 표시 |
| CCM이 오래 옛 버전 | 대시보드에 '전달 대기' 표시(끊긴 CCM은 기존 침묵 경보가 담당) |
| 평가 시간 초과(서버 10초) | 503, 적용 안 함 |

## 11. 테스트

- 레지스트리: 서버·펌웨어 사본 동일(sync_edge_core --check), 기본값이 관계 규칙·한계 통과,
  한계 밖·관계 위반·빠진 키·모르는 키 각각 거부.
- 시나리오: 같은 시드 → 같은 시계열, **기본값으로 사고 6/6 탐지·함정 오경보 0**(CI 기준선).
- 패리티: 기본값 + 무작위 설정 20개에서 파이썬·JS 성적표·사건 시각 일치.
- 관문: 놓치는 설정 거부(예: 벤트 기준을 한계 가까이 올리고 H2·VOC 가중치를 낮춰 1번을 놓치게 만든 설정), 조작된 요청(한계 밖 값) 거부,
  base_version 충돌 409.
- 서버 재설정: 활성화 후 판넬 상태 유지(열린 벤트가 기준 변경만으로 닫히지 않음).
- CCM 단위: 적용·거부·저장·재부팅 후 복원·첫 판정 예외 시 되돌림.
- 종단(실제 HTTP): 적용 → CCM 수신·적용 → 서버에 v 적용 기록, 한계 밖 설정 강제 주입 → CCM 거부 기록.

## 12. 범위 밖

- 판넬·현장별 다른 기준(전체 한 벌만).
- 여러 계정·권한 분리(현재 단일 로그인. 작성자는 로그인 아이디로 기록).
- 실센서 기록 재생(형식만 맞춰 두고, 기록이 생기면 시나리오 파일로 추가).
- 입력 보호·접점 학습 파라미터 튜닝.
